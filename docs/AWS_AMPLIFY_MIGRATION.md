# AWS Amplify + App Runner migration (preview only)

Status: configuration prepared on `migration/aws-amplify-preview`. No production deployment has been triggered.

## Why two AWS services are used

Amplify Hosting is the static React/Vite/PWA frontend host. Angel also has a substantial Express API in `server.ts`; Amplify static hosting does not run that arbitrary long-lived Express server. App Runner is the proposed managed Node.js host for the API. This keeps the existing API routes together while moving off Vercel. The services must be connected with an Amplify rewrite after App Runner provides its HTTPS service URL.

## 1. Create the new Amplify app

1. Open AWS Amplify in the same AWS account/region where you checked the credits.
2. Choose **Create new app → Host web app → GitHub**.
3. Authorize AWS Amplify for the repository `DanielNO-lang/Angel-ai-New`.
4. Select branch `migration/aws-amplify-preview`, not `main`.
5. Keep automatic production publishing disabled for `main`; this is a preview migration branch.
6. Confirm Amplify detects `amplify.yml`. Build output is `dist`, generated by `npx vite build` only. The Express server bundle is intentionally not generated into the static hosting build.

## 2. Create the App Runner backend

1. In AWS App Runner, choose **Create service → Source code repository** and connect the same GitHub repository.
2. Select `migration/aws-amplify-preview`.
3. Use the managed Node.js runtime and the repository's `apprunner.yaml` configuration.
4. The service build runs `npm install` and `npm run build`; start command is `node dist/server.js` on port `3000`.
5. Set the server-side environment variables in the App Runner service configuration, not in GitHub or `apprunner.yaml`. Use **Secrets Manager or Parameter Store** for secret values where available.
6. Wait for the service to become healthy and test `/api/health`. Record the HTTPS service URL. Do not connect the frontend to it until this health check succeeds.

## 3. Configure Amplify environment variables

In **Amplify → App settings → Environment variables**, set only browser-safe values:

- `VITE_SUPABASE_URL`: the URL for the existing Supabase project.
- `VITE_SUPABASE_PUBLISHABLE_KEY`: the Supabase publishable/legacy anon key. This key is designed for browser use and must be protected by correct RLS policies.

Never put `SUPABASE_SERVICE_ROLE_KEY`, `GEMINI_API_KEY`, `OPENAI_API_KEY`, GitHub tokens, webhook secrets, or any other private key in Amplify frontend variables. Vite variables prefixed with `VITE_` are embedded into browser assets and are public.

## 4. Configure App Runner environment variables

Use the existing `.env.example` as the variable-name inventory. Set values only when the feature needs them:

**Core AI**
- `GEMINI_API_KEY` (needed for Gemini-powered generation)
- `OPENAI_API_KEY` (optional provider fallback)

**Supabase**
- `SUPABASE_URL`
- `SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY` (server-only, privileged; never expose to the browser)

**Admin and integrations**
- `ADMIN_EMAILS` (comma-separated allowlist for admin-only integration routes)
- `GITHUB_TOKEN`, `GITHUB_REPO_OWNER=DanielNO-lang`, `GITHUB_REPO_NAME=Angel-ai-New` only if GitHub integration features are required
- `OUTBOUND_WEBHOOK_URL`, `WEBHOOK_SECRET` only if outbound automations are configured
- `WEBHOOK_CALLBACK_ALLOWLIST` with exact approved callback hostnames, only if callbacks are required
- `ZAPIER_OUTBOUND_WEBHOOK_URL`, `ZAPIER_WEBHOOK_SECRET` only if using the legacy Zapier integration

Do not create replacement Supabase credentials or change the existing Supabase project as part of the hosting migration. Verify the current project's Auth redirect URLs and Google OAuth settings separately after the preview hostname exists.

## 4A. Where to obtain each value

- `GEMINI_API_KEY`: Google AI Studio → **Get API key**. Create/use a key in the Google account that owns the Gemini project and check that API access/billing is enabled.
- `OPENAI_API_KEY` (optional): OpenAI Platform → **API keys**. Only add it if you want the OpenAI provider fallback.
- `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`: Supabase Dashboard → the existing Angel project → **Project Settings → API** (the labels may show publishable/secret keys in newer projects). The publishable/anon key is browser-safe; the service-role/secret key is privileged and server-only.
- `GITHUB_TOKEN` (optional): GitHub → **Settings → Developer settings → Personal access tokens**. Use the minimum repository permissions required for the specific integration features.
- `OUTBOUND_WEBHOOK_URL` (optional): copy it from the trigger/catch-hook page of the automation service you actually use. Do not guess a webhook URL.
- `WEBHOOK_SECRET` and `ZAPIER_WEBHOOK_SECRET`: create strong random values in a password manager or secrets manager, then use the same secret on the corresponding sender/receiver. Never commit these values.
- `ADMIN_EMAILS`: enter the exact account email(s) that should be allowed to use admin-only integrations, separated by commas.
- `WEBHOOK_CALLBACK_ALLOWLIST`: enter only the exact callback hostnames you intentionally trust, separated by commas. Do not use broad wildcards.

Do not paste private API keys into this chat or commit them to the repository. Enter them directly in the AWS console's secrets/environment configuration. If a key has already been exposed publicly, revoke it and create a replacement.

## Cost and usage guardrail

The reported AWS credit balance is the user's dashboard figure, not an independently verified balance. App Runner can accrue ongoing charges while the service is running, and Amplify builds/hosting may also consume usage. Review the estimated costs and billing alert thresholds in AWS before creating or leaving services running. Stop or delete preview resources when testing is complete if they are no longer needed.

## 5. Route frontend API requests to App Runner

After App Runner health check passes, open **Amplify → App settings → Rewrites and redirects** and add an API rewrite above the SPA fallback:

- Source address: `/api/<*>`
- Target address: `https://YOUR-APP-RUNNER-SERVICE-URL/api/<*>`
- Type: `200 (Rewrite)`

Replace the target with the actual App Runner HTTPS hostname. Then add/retain the SPA fallback:

- Source address: `/<*>`
- Target address: `/index.html`
- Type: `200 (Rewrite)`

Keep the API rule above the SPA fallback so API calls are not served `index.html`. Do not commit a guessed App Runner hostname.

## 6. Verification gates

Before calling the migration ready, verify all of these on the preview environment:

- Amplify build passes and the PWA loads.
- App Runner `/api/health` returns HTTP 200 and `status: ok`.
- Amplify `/api/health` reaches App Runner through the rewrite.
- `/api/ai/providers` responds.
- Supabase email/Google auth, workspace sync, chat persistence and RLS ownership pass end-to-end tests.
- Gemini chat and streaming pass with a real configured key.
- Workflow approval/cancel, reading, voice, media and webhook paths are tested individually.
- Mobile navigation and PWA installation are tested on actual devices before claiming device support.

## 7. Remaining external steps

The connected tools in this session do not provide AWS Amplify/App Runner account management, so creating the AWS app, authorizing GitHub, adding secrets, and launching the services must be completed in the AWS Console. This branch prepares the repository configuration, but no AWS service has been created or deployed by these changes.

Do not merge this branch to `main` or deploy production until the preview passes and explicit production authorization is given.
